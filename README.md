# wmoop.js

**The TypeScript binding of [WMOOP](https://github.com/WMOOP) — *World Map Object-Oriented
Programming*.**

This is the **TypeScript twin** of [`wmoop.net`](https://github.com/WMOOP/wmoop.net) and
[`wmoop.py`](https://github.com/WMOOP/wmoop.py): the *same* World Model, with the same domains, the
same cross-domain `Person`→`Driver` example and the same design patterns, in idiomatic TypeScript.
It runs on Node.js, and the generated code uses only the language, so it runs in a browser too.

> The canonical model and all design documents live in
> [`wmoop.doc`](https://github.com/WMOOP/wmoop.doc). The data classes here are **generated** from
> the WML model by [`wmoop.tools`](https://github.com/WMOOP/wmoop.tools); this repo adds only the
> behaviour, the design patterns, the demos and the runner of the shared conformance vectors.

## Parity with the other bindings

| Concept | C# (`wmoop.net`) | Python (`wmoop.py`) | TypeScript (`wmoop.js`) |
|---------|------------------|---------------------|-------------------------|
| Generated data classes | one project per domain, a `partial class` per concept | one module per domain in the `wmoop` namespace package | one ES module per domain, `wmoop/<domain>` |
| Hand-written behaviour | the other half of the `partial` class | a `<Name>Ext` mixin in `wmoop_ext.<domain>` | `extend(Class, { ... })` in `src/ext/<domain>.ts`, typed by module augmentation |
| Construction | `required` / `init` properties, object initializers | keyword-only arguments | one `<Name>Init` object |
| Value objects | `readonly struct` | `@dataclass(frozen=True)` | frozen classes with `equals()` |
| Enumerations | `enum` | `str` `Enum` | a frozen object of model ids, and a union type |
| Roles by composition | `AddRole` / `GetRole<T>()` | `add_role` / `get_role(T)` | `addRole` / `getRole(T)` |
| Relations, inverse kept in step | `Links<T>` and property setters | `LinkSet` and `One` / `Many` descriptors | set-like `Links<T>` and accessors |
| Design patterns | `Wmoop.Patterns` and `Wmoop.Patterns.Demo` | `wmoop.patterns` and `patterns_demo.py` | `src/patterns.ts` and `src/patterns-demo.ts` |
| Visitor hook | interface `IAreaVisitor` | `typing.Protocol` (`AreaVisitor`) | interface `AreaVisitor` |
| Specification combinators | `.And()/.Or()/.Not()` | `&` / `\|` / `~` dunder operators | `.and()` / `.or()` / `.not()` methods |
| Generics | `ISpecification<T>` | `Generic[T]` | `Specification<T>` |
| Errors | `IWmoopError.Code` | `WmoopError.code` | `WmoopError.code` |
| Conformance | `Wmoop.Tests` runs the shared vectors of `wmoop.doc` | `conformance.py` runs the same vectors | `src/conformance.ts` runs the same vectors |

Same semantics, idiomatic surface. That is exactly the "write once, replicate everywhere" story.

## Layout

```
wmoop.js/
├── generated/              # GENERATED by wmoop.tools from the pinned model; never hand-edited
│   ├── wmoop/              # _kernel.ts + one module per domain (core.ts re-exports the kernel)
│   ├── package.json        # marks the modules as ES modules
│   ├── tsconfig.json       # checks them on their own, strictly, without Node.js types
│   └── WMOOP_SOURCE.json   # the wmoop.doc / wmoop.json / wmoop.tools commits it came from
├── src/
│   ├── ext/                # behaviour added to the generated classes
│   │   ├── index.ts        # loads every extension module; import it first
│   │   ├── nature.ts       # Person.ageOn
│   │   ├── transport.ts    # describe / classification per vehicle kind, Driver.canDrive
│   │   └── geography.ts    # AreaVisitor; totalPopulation and accept on the areas
│   ├── patterns.ts         # Visitor, Specification, Builder, Strategy, Registry
│   ├── demo.ts             # cross-domain roles + polymorphism walkthrough
│   ├── patterns-demo.ts    # one section per design pattern, self-checking
│   └── conformance.ts      # runs the shared conformance vectors from external/wmoop.doc
├── package.json            # build and test scripts; TypeScript and the Node.js types
├── tsconfig.json           # compiles generated/wmoop and src into dist/
└── external/               # git submodules: wmoop.doc (the model), wmoop.tools (the generator)
```

## Run

Requires **Node.js 20+**. The conformance vectors come from the `external/wmoop.doc` submodule, so
clone with `--recurse-submodules` (or run `git submodule update --init`).

```bash
npm ci
npm run build          # tsc: generated/wmoop and src into dist/
npm run demo
npm run patterns-demo  # one section per design pattern; exits non-zero on failure
npm run conformance    # the shared conformance vectors; exits non-zero on failure
npm test               # all three
```

## Conformance

The checks are not written here. They are the shared conformance vectors of
[`wmoop.doc/conformance`](https://github.com/WMOOP/wmoop.doc/tree/main/conformance), written once
as data and run by every binding, so `wmoop.js`, `wmoop.py` and `wmoop.net` provably agree.
[`src/conformance.ts`](src/conformance.ts) reads the bundle `external/wmoop.doc/conformance/suite.json`:

- A model type resolves through the generated `WM_ID`.
- A model name such as `wheelCount` matches the member `wheelCount`: equal ignoring case and
  underscores, as in every runner.
- An error matches by its registry code (`WmoopError.code`).
- TypeScript's checks do not exist at runtime. The generated code checks what the model states
  itself, so a missing required property or an abstract class is refused by the code, with the
  model's code (`WM-REQUIRED-MISSING`, `WM-ABSTRACT-INSTANTIATION`).

A `pending` vector describes a rule the model has and no binding enforces yet. It is reported
but does not fail the run. Because the vectors are pinned with the model, a regeneration that
brings new vectors also runs them. To add or change a check, add a vector in `wmoop.doc`, not a
test here.

## Generated binding

`generated/` is generated by [`wmoop.tools`](https://github.com/WMOOP/wmoop.tools) from the
canonical model in [`wmoop.doc`](https://github.com/WMOOP/wmoop.doc). Both repos are pinned as git
submodules, `external/wmoop.doc` and `external/wmoop.tools`, and `generated/WMOOP_SOURCE.json`
records the exact commits it was generated from.

Behaviour is added to a generated class with the kernel's `extend()`, and its types are declared by
augmenting the generated module. Both go in the same hand-written file:

```ts
// generated/wmoop/transport.ts: generated, never edited
export class Moped extends Motorcycle {
  ...
}

// src/ext/transport.ts: hand-written
declare module "../../generated/wmoop/transport.js" {
  interface Vehicle {
    readonly classification: string;
  }
}

extend(Vehicle, { get classification() { return "vehicle"; } });
extend(Moped, { get classification() { return "moped"; } });
```

`extend()` defines the members on the class's prototype, so they are inherited down the generated
chain, and a subclass's own `extend` overrides them (`super.describe()` reaches the parent's). It
refuses a member the class already has. `src/ext/index.ts` imports every extension module. Import
it once, before using the classes.

- **Never edit `generated/` by hand.** CI regenerates it from the pins and fails on any difference.
  - To change data, change the model in `wmoop.doc` (or the generator in `wmoop.tools`).
  - To add behaviour, add or extend a module in `src/ext/`, and import a new one in
    `src/ext/index.ts`.
- **Regeneration is automatic.** When `wmoop.doc` or `wmoop.tools` changes, and daily,
  [`regen.yml`](.github/workflows/regen.yml) moves both pins to upstream `main`, regenerates, builds,
  runs the tests and opens (or updates) one `chore(regen): …` pull request.
- **To regenerate by hand** after moving a pin, you need Python 3.10+ and
  `pip install -r external/wmoop.doc/schema/requirements.txt`:

  ```bash
  git submodule update --init                        # external/wmoop.doc, external/wmoop.tools
  git -C external/wmoop.doc submodule update --init  # the grammar the model validator reads
  python external/wmoop.tools/tools/regen_binding.py --lang typescript
  ```

Sometimes the model changes in a way an extension relies on, for example a renamed property. The
regeneration run then fails its build or tests and opens no pull request. A human moves the pins on
a branch, regenerates and updates the extension. Generated code never needs a manual edit
([docs/03-architecture.md §4.4](https://github.com/WMOOP/wmoop.doc/blob/main/docs/03-architecture.md)).
